Policy optimisation

Implemented algorithm core

The update is
part of the system.

Curvature, target bias and data reuse are explicit in these implementations. The interesting part is what happens between collecting a transition and accepting a new policy.

PPO / On-policy

Clipped probability-ratio objective

Gaussian policy, clipped surrogate, entropy regularisation, minibatch epochs, separate value regression and gradient-norm clipping.

SAC / Off-policy

Entropy-regularised actor–critic

Twin Q networks, a stochastic Gaussian actor, replay-buffer updates, a target value network and learned entropy temperature.

TRPO / Trust region

Curvature without a dense Hessian

(HKL + λI) Δθ = gHessian–vector products + conjugate gradients
  1. 01

    Differentiate

    g = ∇θ L(θ)

    Flatten autograd derivatives of the policy-ratio surrogate.

  2. 02

    Solve

    v → Hₖₗv + λv

    Differentiate the gradient–vector product; solve iteratively with residual-based termination.

  3. 03

    Scale

    ½ ΔθᵀHΔθ ≤ δ

    Scale the candidate step using the KL curvature estimate.

  4. 04

    Accept / revert

    KL budget ∧ improvement

    Backtrack until the surrogate improves inside the trust region; restore the old parameters if no candidate passes.

Runtime contract

Deployment architecture · specified in README

A policy export
is a control interface.

The industrial design carries a trained policy into an inference-only runtime with declared shapes, normalisation, action bounds, timing and fallback responsibilities.

  1. 01

    Train

    Python / JAX → frozen parameters

    Version the experiment, data assumptions and policy checkpoint.

  2. 02

    Package

    model.onnx + metadata.json

    Bind the exported graph to the observation/action contract and model hash.

  3. 03

    Execute

    acquire → normalise → infer

    A fixed-tick C++20 runtime with preallocated working buffers is the target execution design.

  4. 04

    Constrain

    clamp → rate / jerk → action

    Monitor validity and timing; signal the classical-control path when takeover is required.

How the learned policy gets control authority

Shadow

u = uclassical

The learned policy observes and logs counterfactual actions. The classical controller retains command authority.

Compare proposed actions with the actual execution before handover.

Residual

u = guard(uclassical + Δupolicy)

The learned policy contributes a bounded correction over the classical controller. The combined command passes through the actuator envelope.

Bound the residual and define the trigger for returning to the classical controller.

Primary

u = guard(upolicy)

The learned policy supplies the main action within the declared execution envelope. Deadline, novelty and input monitors can request fallback.

Control authority depends on runtime validity and a defined takeover path.

Cooperative

u = guard(blend(uclassical, upolicy))

A scheduler coordinates the contribution of classical and learned policies. Blending and transitions become explicit parts of the controller design.

The scheduler owns the handover; actuator constraints still apply to the result.
README acceptance targets

Python/C++ parity ≤ 10⁻⁵ L∞; p95 inference ≤ 2 ms on reference hardware; zero post-init allocations; no missed ticks at the target rate; comparison against a classical baseline.

These are design gates for the deployment track, not reported benchmark results.

01 / Experimental implementation

Model-based learning & simulation

  • Wrote JAX/Flax dynamics and stochastic-policy modules. The dynamics network returns separate mean and log-variance predictions; the policy uses a tanh-squashed Gaussian with clipped log standard deviation and explicit random-key handling.
  • Set up the MBPO architecture around separate real and model replay paths, rollout-length configurations and ablation scripts. The integrated ensemble training and model-rollout loop remain experimental work.
  • Built a Franka manipulation scene in Isaac Sim with USD assets, articulated joints, rigid-body props, collision and friction configuration, surface-gripper control and joint-state input.
02 / Implementation

Second-order policy optimisation

  • Implemented the TRPO policy-ratio surrogate, flattened autograd gradients and conjugate-gradient solving with residual-based termination.
  • Computed damped KL Hessian–vector products through higher-order autograd, avoiding explicit construction of a dense Hessian.
  • Scaled the candidate step to a KL budget, backtracked for surrogate improvement, and restored the previous parameters when no step passed.
  • Implemented PPO with Gaussian action log probabilities, minibatched clipped ratios, entropy regularisation, value regression and gradient clipping.
03 / Implementation

Ensemble value estimation & experience reuse

  • Implemented REDQ with 10 critics, a random 2-critic target subset and a configured update-to-data ratio of 20.
  • Used the subset minimum for target estimation, the ensemble mean in the policy objective, learned entropy temperature and soft target updates.
  • Built TD3, SAC and value-learning implementations spanning Double/Dueling DQN, prioritised replay and Rainbow, alongside tabular planning, Dyna-Q and prioritised sweeping.
04 / Research direction

From learned dynamics to industrial world models

  • The RLx-Core and RLTK roadmaps extend model-based control through MBPO, PETS and PlaNet into Dreamer V1/V2/V3, MuZero and SimPLe.
  • The industrial research questions include long-horizon manipulation, partially observed machine state, failure prediction, experience reuse and adaptation across tasks.
  • The wider programme includes offline and imitation learning, hierarchical skills, multi-agent coordination, sequence-model policies, robust sim-to-real transfer and risk-sensitive control.
  • The deployment design binds a policy to observation normalisation, actuator bounds, model identity, timing assumptions and Shadow, Residual, Primary or Cooperative operating modes.
Engineering note

Prediction becomes useful when it changes a control decision.

A world model needs to retain the dynamics that matter for action: contact, timing, hidden state and how errors compound over a rollout. That connects the research back to controller design. The policy needs a useful imagined future; the runtime still needs an action it can execute, a deadline it can meet and a defined response when its assumptions fail.
